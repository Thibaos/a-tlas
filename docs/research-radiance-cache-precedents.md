# World-space radiance cache precedents (ticket 01)

## Executive answer

Every published world-space cache splits on the same axis: **probes in free space** (DDGI, Ward's irradiance cache, Radiance Cascades) vs **entries keyed to surfaces** (SHaRC's spatial hash of voxels, VXGI/Tomorrow Children cascaded anisotropic voxels, sparse-octree voxel radiance shooting). atlas-rt already has the thing the probe methods spend all their machinery approximating: **exact surface positions and normals from DDA hits**. That eliminates DDGI's entire complexity budget — probe relocation, Chebyshev-visibility bias terms, fallback probes, tetrahedral/trilinear interpolation — none of which buys anything when the key is the hit face itself. The shortlist:

1. **Dense per-face cache inside the existing voxel pool** (VXGI-anisotropic-voxel granularity without the cones): one entry per exposed voxel face, `RGBA16F` = 8 B (RGB outgoing irradiance + alpha as age/sample-count), exponential moving average toward the frame's hit radiance, only hit faces update, stale entries age out via the alpha channel. No hashing, no compaction, O(1) lookup straight off the DDA hit. This is candidate #1.
2. **SHaRC-style spatial hash grid** (NVIDIA RTXGI v2, shipped): logarithmic-level hash keys from `(position, normal)`, Update/Resolve/Query passes, 64-bit key + 2×128-bit data slots. The right choice if dense face storage is too big or faces need multi-scale entries. Candidate #2.
3. **DDGI probe volumes**: rejected as primary. Its failure modes (leaking through thin geometry, ringing from octahedral SH compression, temporal lag from hysteresis, probe-position/relocation problems) are all artifacts of sampling light *off* the surface. Worth stealing only its update policy: hysteresis/exponential blend (~0.9–0.95 old-weight) plus border/clamp handling.

Storage math per face entry: `RGBA16F` = 8 B/face. A voxel exposes ≤ 6 faces; terrain-like worlds average ~1–3 exposed faces per occupied voxel, so ~8–24 B/occupied voxel, i.e. 512³ at 10% occupancy ≈ 26k occupied voxels ≈ 0.2–0.6 MB. Even full 6-face allocation is 48 B/voxel ≈ 1.3 MB — trivially affordable. A SHaRC hash alternative costs ~28–32 B/slot before occupancy (64-bit key + 128-bit data + 128-bit previous-frame + 32-bit copy offset), roughly 3× the dense cost at equal coverage, spent to gain sparsity we don't need because the Occupancy mask *is* the sparsity map.

## Findings

1. **Ward's classic irradiance cache (1988/92): records at scattered surface points, gradient-corrected interpolation, validity radii.** Records store irradiance + translational/rotational gradients computed almost free from hemisphere samples; a record is reused within a validity radius derived from gradients and geometry; lookup walks an octree independent of surfaces. Keyed to arbitrary surface points — the "where do I put records" problem is intrinsic. [Irradiance Gradients](https://radsite.lbl.gov/radiance/papers/erw92/paper.pdf), [Irradiance Caching Algorithm slides](https://cgg.mff.cuni.cz/~jaroslav/papers/2008-irradiance_caching_class/03-greg-ic.pdf)

2. **DDGI (JCGT 2020, NVIDIA RTXGI): regular 3D grid of probes storing octahedral-mapped irradiance (+ distance), updated every frame with hysteresis.** Each probe stores an N×N octahedral atlas (typically 8×8 texels incl. 1-texel border) in texture arrays; new ray radiance is integrated and blended with the previous frame (`hysteresis`, exponential decay); reads use trilinear (or cheaper tetrahedral, 4 samples vs 8) interpolation of the 8 surrounding probes with a normal-dot weight. Failure modes are documented extensively: light leaking (mitigated by Chebyshev distance-visibility testing against probe depth maps), ringing (octahedral texel clamping during integration), temporal lag from aggressive hysteresis, and probe-inside-geometry handled by **probe relocation** (offsetting probes along sampled min-distance directions) and **probe classification** (infinite/invalid states). Fallback/dummy probes fill gaps where no valid neighbor exists (Flax Engine added dedicated ambient fallbacks). [DDGI JCGT paper](https://jcgt.org/published/0008/02/01/), [RTXGI DDGIVolume docs](https://github.com/NVIDIAGameWorks/RTXGI-DDGI/blob/main/docs/DDGIVolume.md), [RTXGI Irradiance.hlsl](https://github.com/NVIDIAGameWorks/RTXGI-DDGI/blob/main/rtxgi-sdk/shaders/ddgi/Irradiance.hlsl), [Flax fallback commit](https://git.flaxengine.com/Flax/FlaxEngine/commit/c5a28a5734ff9a132b278efd23a08a8cdd56e3da), [CESCG probe improvements](https://cescg.org/wp-content/uploads/2022/04/Rohacek-Improving-Probes-in-Dynamic-Diffuse-Global-Illumination.pdf)

3. **SHaRC (NVIDIA RTXGI v2, 2023): world-space spatially-hashed voxel cache, exactly the surface-keyed shape.** Keys come from `(world position snapped to voxel, normal)` hashed into a 64-bit key over **logarithmic grid levels** (Jendersie's logarithmic caching); fixed-size GPU buffers hold Hash Entries (64-bit keys, bucket size 32 with linear-search collision resolution), Voxel Data (128-bit packed accumulated radiance + sample count, integer accumulation scaled by `SHARC_RADIANCE_SCALE`), Voxel Data Previous (128-bit, for temporal resolve), Copy Offset (32-bit, compaction). Three passes per frame: **Update** (sparse trace populates cache, with signal backpropagation depth ~4 so late path vertices write earlier-path cache entries), **Resolve** (combine new accumulation with previous frames), **Query** (hits read the cache for early termination). Stale entries are aged out and compacted. This is the shipped reference for "per-surface-entry world-space cache on a single consumer GPU". [SHARC repo](https://github.com/NVIDIA-RTX/SHARC), [Integration docs](https://github.com/NVIDIA-RTX/SHARC/blob/main/docs/Integration.md), [SharcCommon.h](https://github.com/NVIDIA-RTX/SHARC/blob/main/include/SharcCommon.h), [HashGridCommon.h](https://github.com/NVIDIA-RTX/SHARC/blob/main/include/HashGridCommon.h)

4. **Neural Radiance Cache (NRC, NVIDIA 2021): replaces the storage entirely with a tiny fused MLP trained online per frame.** Input features include hit position/normal/direction/material plus per-frame hashes; short paths terminate early and read the network, long paths train it; no explicit cache points, no interpolation, no thrash — but it needs the training infrastructure and has its own temporal-stability quirks, and AMD's competing FSR Radiance Cache follows the same online-ML shape. Not a fit for this codebase's single-shader-file, deterministic-RNG constraints. [NRC paper](https://jannovak.info/publications/NRC/NRC.pdf), [NRC library](https://github.com/NVIDIA-RTX/NRC), [AMD FSR Radiance Cache](https://gpuopen.com/manuals/fsr_sdk/techniques/radiance-cache/)

5. **Voxel cone tracing / cascaded anisotropic voxel caches: per-voxel-per-face-direction radiance in dense/cascaded 3D textures.** Crassin's VXGI stores outgoing radiance + opacity in a sparse octree with bricks, 6 direction bins per voxel (anisotropic); The Tomorrow Children shipped 6 cascades of 32³ voxels, anisotropic (6 facing directions), packed into single 3D textures, after their first non-texture attempt ran 30+ ms and was abandoned ("just use a 3D texture"). The 6-direction-per-voxel layout is precisely a **per-voxel-face key**, and the precedent says: make it a plain 3D texture/array indexed by the voxel coordinate, not a pointer structure. Failure modes: memory blowup with resolution (hence cascades), cone-trace soft leaking, temporal lag on lighting changes. [Crassin 2011](https://onlinelibrary.wiley.com/doi/10.1111/j.1467-8659.2011.02063.x), [Tomorrow Children slides](https://fumufumu.q-games.com/archives/Cascaded_Voxel_Cone_Tracing_final.pdf)

6. **Sparse-octree voxel radiance shooting: radiance stored only on occupied cells, few direction bins, iterative propagation.** Memory reduced by storing only on occupied SVO cells and sampling ~24 propagation direction bins; propagation compensates for bin solid angle and supports anisotropic scattering. Confirms that surface-only storage plus a small directional basis is a viable published shape. [Global illumination in sparse voxel octrees](https://dl.acm.org/doi/10.1007/s00371-021-02078-6)

7. **Radiance Cascades: hierarchical screen-space/free-space probes; wrong key for this renderer.** RC represents the radiance field over cascades of increasing spatial / decreasing angular resolution, originally 2D screen-space, 3D variants exist; memory in 2D bounded by 2× cascade 0. It solves "cover free-space visibility cheaply" — a problem atlas-rt doesn't have when the key is an exact DDA hit face, and its 3D formulations remain experimental. [Radiance wiki / original paper](https://radiance.wiki/papers/sannikov-original)

8. **Update policy consensus: exponential/hysteresis blend, not replacement.** DDGI blends probe texels with hysteresis; SHaRC resolves new accumulation against previous-frame data with aging; Tomorrow Children accumulated over time in the 3D texture. At 1 spp the blend factor sets the noise/lag tradeoff directly: weight w on the new sample gives an effective window of ~1/w frames. DDGI uses ~0.05–0.1 new-sample weight; anything higher re-noises the cache, lower smears moving lights.

9. **Read path: no interpolation needed for exact-hit keys.** Ward/DDGI interpolate because queries land between records. When the cache is keyed by the hit face itself, the read is a direct fetch — the interpolation question disappears, which is what makes the dense per-face option both simplest and artifact-free. Gradient correction (Ward) exists to extend validity between records and is likewise moot. [Ward gradients](https://radsite.lbl.gov/radiance/papers/erw92/paper.pdf), [RTXGI Irradiance.hlsl](https://github.com/NVIDIAGameWorks/RTXGI-DDGI/blob/main/rtxgi-sdk/shaders/ddgi/Irradiance.hlsl)

## Shortlist (ranked)

1. **Dense per-exposed-face cache piggybacked on the voxel pool.** Key = global voxel coord + face axis (3 bits); value = RGBA16F (RGB outgoing irradiance, alpha = recency/sample count); update = EMA toward the bounce-hit radiance gathered by paths that pass through the pixel; unhit faces simply don't update and decay in alpha. Direct index, zero hashing, zero compaction, zero interpolation. Matches the Tomorrow Children lesson ("just use a 3D texture") at micro-chunk granularity.
2. **SHaRC-style logarithmic spatial hash** if dense proves too large or multi-scale caching is wanted later; costs ~3× storage and adds Update/Resolve/compaction passes but is shader-only and battle-tested (RTXGI).
3. **DDGI** only if a cache decoupled from the voxel representation is ever needed (e.g., dynamic non-voxel lights) — rejected otherwise for the reasons in finding 2.

Per-face storage math: 8 B/face (RGBA16F); worst case 6 faces = 48 B/occupied voxel; realistic ~16–24 B; 512³ @10% ≈ 26k voxels ≈ 0.4–0.6 MB; 2048³ @10% ≈ 1.7M voxels ≈ 27–41 MB — fits comfortably in VRAM, and scales per-resident-region if allocated region-wise like the voxel pool. SHaRC equivalent ≈ 28–32 B/entry + load-factor overhead.
