# The .vox MATL surface available to atlas-rt (dot_vox 5.2.0, ticket 01)

> Research ticket: transparency-and-overrides ticket 01 (the scratch
> tracker is archived — decision in ADR 0012).
> Verification date: 2026-08-25; dot_vox 5.2.0 (crate pinned `dot_vox = "*"` in Cargo.toml, resolved source read from the local cargo registry cache); MagicaVoxel editor 0.99.7.2 win64 (current release, 7/12/2025) downloaded and dissected: bundled sample `.vox` files parsed byte-by-byte, material-panel UI (`config/ui/r_mtl.ui`) read, editor binary string table scanned. All crate claims verified against actual dot_vox source, none guessed.

## Executive answer

MATL is an opaque DICT chunk — `int32 material id` + `DICT` of string→string pairs — and **dot_vox preserves it losslessly**: `DotVoxData.materials: Vec<Material>` where `Material { id: u32, properties: HashMap<String, String> }`. Nothing is dropped at parse time; the typed accessors are sugar over the raw map. The editor-reachable material types are **diffuse (the reset/default state), metal/plastic, glass, emissive, blend, cloud/media**, with media subtypes absorb/scatter/emissive/subsurface-surface-scattering. The single most important empirical finding: **a plain palette entry carries NO `_type` key at all** — `_type` appears only when the user picks a non-diffuse preset, so `_type == "_glass"` is an explicit, unambiguous authoring signal that survives parsing verbatim via `properties.get("_type")`/`Material::material_type()`. Two hazards for ticket 03: pre-unified-system saves often contain **zero MATL chunks** (absence of glass data ≠ presence), and the default entry's own keys (`{_ior: 0.3, _ri: 1.3, _rough: 0.1}`) are incomplete — a renderer must supply physics defaults itself.

## 1. MATL in the file format

1. **Chunk layout.** `MATL` content = `int32 material id` followed by a DICT (`int32` pair count, then length-prefixed STRING key/value pairs). Values are decimal ASCII strings — integers written without a point (`"_weight": "1"`), floats with (`"_rough": "0.1"`); consumers parse with `str::parse::<f32>()`, which handles both. [MagicaVoxel-file-format-vox-extension.txt](https://github.com/ephtracy/voxel-model/blob/master/MagicaVoxel-file-format-vox-extension.txt)
2. **The official spec is 2016-stale.** It documents only `_diffuse, _metal, _glass, _emit` types and keys `_weight` (range 0–1), `_rough`, `_spec`, `_ior`, `_att`, `_flux`, `_plastic`, and declares the older numeric `MATT` chunk deprecated. Everything blend/media-related is undocumented officially; ephtracy.github.io just links this same file. [MagicaVoxel-file-format-vox-extension.txt](https://github.com/ephtracy/voxel-model/blob/master/MagicaVoxel-file-format-vox-extension.txt), [ephtracy.github.io/mv_vox_format.html](https://ephtracy.github.io/mv_vox_format.html)
3. **The unified material system (0.99.6.x, June 2020 changelog) is the real target.** Official changelog: "Blend Material : weighted blending Metal/Plastic/Glass/Cloud materials (similar to Disney Principled BRDF)"; "SSS Material : sub-surface scattering. transparency to control light transmission. density to control light scattering"; "Absorb/Scatter/Emissive Media Material : emissive cloud, can be contained in the glass with ior > 1"; "Improved Alpha Blending : glass material, absorb media type, density = 0, ior = 0, transparency > 0". Cloud/media dates to 0.99.4 (2019). Current release 0.99.7.2 (7/12/2025). [ephtracy.github.io changelog](https://ephtracy.github.io/)
4. **Ground truth from the 0.99.7.2 binary's string table** (one contiguous table, `MagicaVoxel.exe` @ 0x319690): type tokens `_diffuse _emit _blend _metal _glass _media`; media-type tokens `_absorb _scatter _sss` (only three — the UI's fourth "Emissive Media" option has no dedicated token); property keys `_type _weight _rough _sp _spec _spec_p _ior _ri _att _emit _ldr _flux _alpha _trans _d _g0 _g1 _gw _plastic _media_type`. Note `_pn` and `_glow` are absent from the 0.99.7.2 binary (they appear only in older third-party fixtures). Verified by scanning the shipped executable, not inferred.

## 2. What the editor writes per palette entry (empirical)

Parsed every `.vox` bundled with MagicaVoxel-0.99.7.2-win64.zip (15 files: monu1–3, room, castle, cars, doom, teapot, chr_knight, menger, T-Rex×2, Gomez, deer, 3x3x3):

1. **Modern saves carry exactly 256 MATL chunks each, ids 1…256 inclusive** — one per palette slot, written unconditionally, not only for edited materials. (Older third-party fixtures in the dot_vox repo use ids 0…255; do not assume a fixed base — match MATL id to the voxel colorIndex convention you use for the RGBA palette.)
2. **Default/unmodified entry = no `_type` at all**: `{_ior: "0.3", _ri: "1.3", _rough: "0.1"}` (2295 of 3840 entries across the bundle). Diffuse/plastic is the implicit reset state — the UI exposes it only as "Reset to Diffuse Material [CTRL+R]", not a tab. Consequences: (a) absence of `_type` must be treated as diffuse, never as "no data"; (b) the written defaults are renderer-flavored hints, not physics — `_ior 0.3` is a normalized slider, `_ri = 1 + _ior` is the actual refractive index (1.3 ≈ water-ish; the editor writes `_ri` explicitly alongside `_ior`, verified across all variants: 0.32→1.32, 1.0→2.0).
3. **Metal**: `_type: "_metal"` plus `_rough/_ior/_ri` and the metallic slider `_metal` (observed 0.5 and 1.0); `_plastic: "1"` appears in older-version fixtures for plastic-mode entries.
4. **Emissive** (room.vox): `_type: "_emit"`, `_emit` (strength, e.g. "1"/"0.23"), `_flux` (radiant power/UI "Power", integer 0–4), plus carried-over `_g`.
5. **Cloud/media params leak onto ordinary entries**: 1289 of 3840 entries carry `_d: "0.05"` (density) and 256 carry `_g: "0.41"` (phase) with no `_type` — these sliders persist per-entry independent of the type preset. No bundled sample contained `_glass`/`_blend`/`_media` entries, so their exact written key sets are verified only structurally (UI panel membership + binary tokens), not from a saved example.
6. **UI panel composition** (`config/ui/r_mtl.ui`, exact bindings): tabs Emit / Blend / Metal ("Metal/Plastic") / Glass / Cloud. Surface panel (Blend+Metal+Glass): Roughness (`pt_rough`), IOR. Metal extra: specular slider `pt_sp` (range 1–2) and Metallic (`pt_metal`). Transparency panel (Blend+Glass): `pt_trans`, bound via `set pt_mtl _trans`. Media panel (Blend+Glass+Cloud): media-type opBox Absorb/Scatter/Emissive/"S"=Subsurface Scattering, Density (`pt_d`), Phase (`menu_g`). Emit panel: Emit (`pt_emit`), Power (`pt_flux`, 0–4 step 1), Ldr (`pt_ldr`). So glass-authored entries are expected to write `_trans` (+ optionally media keys) alongside `_type: "_glass"`; `_alpha` exists in the key table but is not bound in this UI panel (legacy/compositing path).
7. **Version drift is real and binary**: the older samples from ephtracy/voxel-model (monu6.vox with water, ff1.vox fireworks, v150) contain **zero MATL chunks** — water there is just a palette color. Files saved before ~0.99.4 cannot express glass/media at all, and even 2018–2019 saves only emit MATL for touched entries. dot_vox's test fixtures (`placeholder-with-materials.vox`, ~29 KB, v150) show that intermediate era: full 256-entry MATL with `_diffuse` defaults `{_weight: 1, _rough: 0.1, _spec: 0.5, _ior: 0.3}` — note `_spec`, which the modern editor replaced with `_sp`.

## 3. What dot_vox 5.2.0 actually surfaces

Verified against the resolved crate source (`~/.cargo/registry/src/index.crates.io-*/dot_vox-5.2.0/src/`, repo dust-engine/dot_vox, nom 8 / edition 2024):

1. **Container**: `DotVoxData { version: u32, index_map: Vec<u8>, models, palette: Vec<Color>, materials: Vec<Material>, scenes: Vec<SceneNode>, layers: Vec<Layer> }`. `version` is the raw header value (v150 and v200 files both parse; the parser dispatches chunks purely by 4-byte id, never by version). [parser.rs](https://github.com/dust-engine/dot_vox/blob/main/src/parser.rs), [dot_vox_data.rs](https://github.com/dust-engine/dot_vox/blob/main/src/dot_vox_data.rs)
2. **Nothing is dropped.** `pub struct Material { pub id: u32, pub properties: Dict }` with `Dict = HashMap<String, String>` (AHashMap under the default `ahash` feature). Every key/value pair of every MATL chunk round-trips verbatim, including keys the accessors don't know (`_ri`, `_plastic`, `_g0/_g1/_gw`, future keys). Chunks dot_vox doesn't understand (`MATT`, `META`, `NOTE`, `rOBJ`, `rCAM`, `PACK`) hit `Chunk::Unknown` and are logged via `log::debug!` only — silently absent from the output, never fatal.
3. **Typed accessors are Option-returning views over the map**: `material_type()`→`_type` (returns the raw string *including* the leading underscore: `Some("_glass")`), `weight()`→`_weight` (logs a warning outside [0,1] but still returns it), `metalness()`→`_metal`, `roughness()`→`_rough`, `specular()`→`_sp`, `refractive_index()`→`_ior`, `emission()`→`_emit`, `low_dynamic_range_scale()`→`_ldr`, `attenuation()`→`_att`, `radiant_flux()`→`_flux`, `phase()`→`_g`, `opacity()`→`_alpha`, `transparency()`→`_trans`, `density()`→`_d`, `media()`→`_media`, `media_type()`→`_media_type`. Float parsing failures degrade to `None` with a debug log.
4. **Accessor bugs/gaps to route around**: `Material::ri()` documents reading "`_ri`" but actually calls `get_f32("_ior")` — copy-paste bug; read `properties["_ri"]` directly instead. There is no accessor for `_plastic`, `_glow`, `_spec` (legacy spelling of today's `_sp`), or `_g0/_g1/_gw`. Non-fatal, since the raw map has everything.
5. **No defaults are synthesized.** If the file has no MATL chunks, `materials` is simply empty (the `DEFAULT_MATERIALS` 256-diffuse vec exists only inside `#[cfg(test)]`). Every consumer must handle `materials.len() == 0`.
6. **Indexing contract**: `extract_palette` reads the RGBA chunk as raw sequential 4-byte entries into `Vec<Color>` (up to 256); the format spec maps stored color[i] to palette index i+1, and voxel colorIndex 0 means empty — atlas-rt's `get_palette` already enumerates `data.palette` into slots 0..n, so a MATL lookup keyed by voxel colorIndex needs the same offset discipline as the palette (empirically MATL ids ran 1..256 in v200 files, 0..255 in older ones). The IMAP chunk (drag-reorder mapping) is parsed since dot_vox 5.2 into `index_map`.

## 4. Implication for ticket 03 (signal/opacity decision)

Use **`properties["_type"] == Some("_glass")`** (via `Material::material_type()`) as the transparency marker: it is written explicitly by the editor whenever the Glass preset is picked, it is the only glass-specific signal that survives dot_vox parsing intact, and it degrades correctly — files without any MATL chunks yield an empty `materials` vec and entries without a preset yield no `_type`, both mapping cleanly to "opaque diffuse", which is exactly what those files mean. Treat `_trans` (editor Transparency slider) as the transmission amount when present and default it yourself when absent (nothing guarantees the key); ignore palette-color alpha and `_alpha` as opacity signals — material transmission lives exclusively in the MATL dict; and keep `_blend`/`_media` out of the glass bucket even though the Blend tab exposes the same Transparency panel, because they are different compositing/volume semantics. Concretely: build a `[MaterialParams; 256]` table by scattering `data.materials` over their `id`s (handling both the 0-based and 1-based id conventions), resolve each entry as diffuse unless `_type` says otherwise, and require explicit `_glass` for refraction — the cost is that genuinely transparent voxels authored in pre-2020 files render opaque, which is faithful to what those files contain.
