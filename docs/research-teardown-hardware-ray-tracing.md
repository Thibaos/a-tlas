# Hardware ray tracing in "Raytracing Voxels in Teardown and Beyond" (part 2 only)

## Executive answer

The second part of the GPC 2025 talk (Breda, Nov 18–20, 2025) by Dennis Gustafsson and Gabe Rundlett (Tuxedo Labs) presents the **next-generation Tuxedo Labs engine**: a from-scratch Vulkan renderer (built on the Daxa framework) that replaces Teardown's software voxel raytracing with **hardware-accelerated ray tracing**. Voxels are *not* converted to triangles: each object is split into 8×8×8-voxel chunks whose AABBs are inserted into a BLAS as **procedural primitives**, and a **custom intersection shader** runs the classic fast-voxel-traversal DDA inside each chunk. The one-bit shadow volume is eliminated entirely, which the speakers say unlocks unlimited world size, sharp shadows, no light leakage, many dynamic objects at low cost, and true reflections + global illumination; the indexed palette is dropped for per-voxel albedo + PBR properties (BC4-compressed after BC7 failed real-time recompression); denoising uses NVIDIA DLSS Ray Reconstruction. A headline claim, confirmed verbatim in the talk: **ray tracing the primary view was the fastest solution, even on AMD**, beating a GPU-driven re-meshing rasterizer and direct chunk re-marching. "Beyond" = this engine targets an upcoming game, not Teardown.

Scope note: this document covers **only part 2** (hardware ray tracing). Part 1 (Teardown's shipped software renderer: OpenGL 3.3, fragment-shader DDA, one-bit shadow volume) is out of scope except where needed to frame the design decisions. The repo context is a wgpu-based voxel engine (chunked 3D textures, compute-shader DDA), so each finding notes relevance to that where useful.

## Findings

1. **Motivation: the shadow volume caps everything.** Four of the six limitations listed at the end of part 1 (maximum level size, no global illumination, dynamic objects, quantization artifacts) trace directly to the one-bit shadow volume. The desired fix is "the ability to have a precise ray intersection with our actual oriented voxel volumes", which needs "a completely new solution", so "we decided to switch to the obvious, hardware ray tracing", buying "pixel-perfect shadows, really nice reflections, and even global illumination". [Recording, part 2 opening](https://www.youtube.com/watch?v=IM1Dr98f3xU)

2. **API: OpenGL → Vulkan, renderer rewritten from scratch, via Daxa.** Hardware RT requires ditching OpenGL; the renderer was rewritten from scratch. Vulkan brings hardware RT plus DLSS, FSR, and NRD-class denoisers, but is daunting for a small team, so they adopted the open-source **Daxa** framework (created by Patrick Ahrens, co-developed by Matěj Šakmar and Dennis Gustafsson), chosen for its fully bindless resource model, powerful render graph, and removal of explicit render passes. On the DX12 question: Vulkan was a personal preference; Teardown's DX12 backend exists mainly for console support and uses few DX12 features. [Recording](https://www.youtube.com/watch?v=IM1Dr98f3xU), [slides](https://static.graphicsprogrammingconference.com/public/2025/slides/raytracing-voxels-in-teardown/Rundlett-Gustafsson-raytracing-voxels-in-teardown-and-beyond.pdf)

3. **Acceleration structure: procedural AABBs in BLASes + custom intersection shaders, still no triangles.** The scene is still split into oriented volumes, but each volume is now a regular grid of **chunks of up to 8×8×8 voxels**, positioned relative to the object origin (resizing grows/shrinks the grid instead of restructuring it). All chunk AABBs are inserted as **procedural primitives into BLASes, one BLAS per voxel volume**, with the AABBs tightly fitted to the geometry inside the chunk (important for sparse objects like flagpoles). Because the primitives are procedural, a **custom intersection shader** computes the actual hit: it runs the same fast voxel traversal as Teardown but with the mipmapping concept removed, since the volumes are so small that only a few DDA steps are needed before hitting something or exiting. This matches Dennis's earlier first-party blog description: "relies heavily on hardware raytracing (using intersection shaders, **still no triangles!**)". [Recording](https://www.youtube.com/watch?v=IM1Dr98f3xU), [Voxagon blog, "Year summary" (Dec 29, 2024)](https://blog.voxagon.se/2024/12/29/year-summary.html)

4. **The traversal-order problem and how they debugged it.** With hardware RT they have no control over which volume's intersection shader runs first, so traversal work can be wasted on occluded volumes. NVIDIA's RT debugger/traversal-timing tooling was useless here because with custom intersection shaders it only reports worst-case screen-space AABB overlap. Their workaround: the SPIR-V `clockARB` intrinsic (GLSL/Slang), sampled before/after expensive work in the intersection shader and remapped to a heatmap. This showed fully occluded intersection-shader invocations; when the heatmap lit up at a very large scale, that signaled a problem in the **TLAS** (generation or traversal). A concrete TLAS insight: terrain pre-split into irregular shapes by level designers (an optimization for Teardown's empty-space traversal) produces a *worse* generated TLAS than regularly subdividing the terrain grid. The chunking already handles empty space. [Recording](https://www.youtube.com/watch?v=IM1Dr98f3xU)

5. **Primary view: RT beat rasterization, even on AMD.** Revisiting why voxels aren't rasterized (too many faces, gigabyte-scale VRAM for triangles), Gabe implemented the alternatives before settling: (a) a rasterized primary with full GPU-driven occlusion culling that re-meshes only visible voxels every frame, using compute rasterization for quads, **slower than ray tracing the primary ray**; (b) re-marching the chunk AABBs directly (simpler, "should have thought of that before"), faster than re-meshing, but "even after optimizing the ray tracing performance, **even on AMD, ray tracing primary was the fastest solution**". In Q&A: the primary pass is "actually faster than in Teardown", while full path tracing on high-end GPUs "can take like 10 milliseconds even. It's pretty rough." [Recording](https://www.youtube.com/watch?v=IM1Dr98f3xU)

6. **Palette → per-voxel PBR, and the BC7/BC4 saga.** Artists wanted runtime recolorability of any voxel to any color with any PBR properties (roughness, metalness, emissivity, albedo). Naively 6 bytes/voxel ≈ 6× the level VRAM. They made the volume storage sparse (chunked) instead: 4×4×4 chunks use least VRAM, but **8×8×8 rendered faster**, so they accepted the extra VRAM for a unified split between storage and rendering. Block compression was tempting (BC7 for albedo, BC4 per PBR property ≈ Teardown's VRAM); AMD Compressonator results looked excellent offline, but real-time recompression is required (explosions/breakage) and Compressonator's BC7 is too slow; a GPU BC7 encoder (code "stolen from Microsoft") produced bad artifacts, **pink fringing** from non-colinear interpolation endpoints. Verdict: BC7 rejected for now; **BC4 per RGB channel** costs an extra half byte per voxel but lands VRAM at roughly Teardown's level (up to +50%), and once the shadow volume removal is counted, the new engine uses **less VRAM than Teardown on all levels** while storing full per-voxel PBR. In Q&A, block compression gave only ~1% average throughput gain. Traversal, not material sampling, is the bottleneck (PBR data is sampled only in the closest-hit shader). [Recording](https://www.youtube.com/watch?v=IM1Dr98f3xU)

7. **Denoising: NVIDIA DLSS Ray Reconstruction.** First-party blog (about the prototype that became this renderer): "For denoising I've been using NVIDIA DLSS Ray Reconstruction, and overall I've been very pleased with the results. It tends to be a bit aggressive in some scenarios, but still very impressive technology." [Voxagon blog](https://blog.voxagon.se/2024/12/29/year-summary.html)

8. **Deformable voxels.** Voxels don't need to conform to an orthogonal box: the new engine ray traces voxels inside **arbitrarily skewed bounding boxes** (approximate solution. An invertible affine map from a unit cube to an arbitrary deformed cuboid doesn't exist), enabling things like wind-swaying trees that the shadow volume could never support. [Voxagon blog](https://blog.voxagon.se/2024/12/29/year-summary.html)

9. **"Beyond": a full engine rewrite, ~2 people, ~2 calendar years, for an upcoming game.** The renderer is one slice of a total engine rewrite (frameworks included): components/systems architecture (not pure ECS), a "virtual property" system unifying editor UI/serialization/undo-redo/scripting, a lock-free (atomics-based) task manager, and physics substepping with a parallel solver. In Q&A: "just me and Dennis", started ~2 years ago in calendar time (~1 year effective for two people), and, asked directly, **no Teardown 2** on this engine; the new engine "is unlikely to be integrated into Teardown, but intends to use it in upcoming projects." [Voxagon blog](https://blog.voxagon.se/2024/12/29/year-summary.html), [Recording, Q&A](https://www.youtube.com/watch?v=IM1Dr98f3xU), [80.lv: "Teardown Creator Is Working On A New Voxel Engine"](https://80.lv/articles/teardown-creator-is-working-on-a-new-voxel-engine)

10. **Transparency is still open.** Current approach: the main pass casts a G-buffer ray; on hitting a transparent voxel it sends a refracted secondary ray and stores hit position + absorption in the G-buffer; only a single transparency layer, and shadow/GI rays ignore transparent voxels entirely. (Teardown shipped a screen-door checkerboard effect with one transparency level.) [Recording, Q&A](https://www.youtube.com/watch?v=IM1Dr98f3xU)

11. **On hardware voxel intersection support.** They discussed with NVIDIA whether voxel intersection deserves hardware support; the takeaway is that it's too specific a use case, and custom intersection shaders already "break in" to the RT-core flow (the cores must switch to compute work between shader invocations). Both NVIDIA and the speakers "were quite surprised by the performance level we got from this". Dennis: "I would love hardware custom intersection for voxels. That would be awesome." [Recording, Q&A](https://www.youtube.com/watch?v=IM1Dr98f3xU)

## Relevance to wgpu-rt (chunk textures, compute-shader DDA)

- The talk validates the per-pixel ray path wgpu-rt already takes: hardware RT of the primary view beat both a raster proxy pipeline and CPU/GPU re-meshing, so a single ray per pixel with an occupancy hierarchy is a sound target rather than a stopgap.
- The new engine's design maps 1:1 onto wgpu-rt's: chunk AABBs ≈ wgpu-rt's proxy cubes; the chunked-sparse representation is the same trade as occupancy mips vs dense chunk textures; the custom intersection shader does exactly what wgpu-rt's fragment/compute DDA does, minus the mip-level empty-space skip (their chunks are small enough to skip it; wgpu-rt's 256³ chunks are not).
- Practical caveat: there is no portable WebGPU/wgpu ray-tracing API today, so the hardware-RT specifics (BLAS/TLAS, procedural primitives, intersection shaders, clockARB instrumentation) are not directly implementable in wgpu-rt; the transferable lessons are the data-format decisions (sparse chunking, per-voxel color over a global palette, no dense shadow volume, BC4-style compression trade-offs) and the performance thesis (RT primary can beat raster proxies on mainstream GPUs).
- Their debugging technique (wave-wide clock sampling around the traversal, mapped to a heatmap) is directly portable to wgpu-rt's compute shaders for profiling DDA cost per screen region.
